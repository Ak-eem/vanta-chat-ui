**What's solid:**
- Type separation matches how the actual systems do it, not a simplified guess.
- `supersedes` instead of overwrite is the mature call — versioned records instead of a preference silently vanishing or contradicting itself.
- "Working memory = last 8–20 messages" — you don't need to build this part. `conversations[sid]` + `MAX_HIST` already *is* working memory, feeding `build_prompt()` right now. This design is really adding the semantic/episodic/procedural layers on top of something that already exists, not starting from zero.

**Storage — Chroma would repeat a problem you already solved.** Check `rag.py`'s own docstring: you already tried Chroma for the knowledge base and dropped it specifically because its default embedder downloads a 79MB ONNX model on first run, and that timed out on your connection — that's the actual reason `rag.py` is keyword-matching instead. Proposing Chroma again for memory risks hitting the exact same wall you already worked around once. `sqlite-vec` is the right call here, not just generically — specifically because it sidesteps the failure mode you've personally already hit.

**"Embeddings run local" — worth a second look, and not for the reason you'd expect.** I checked: OpenRouter actually does have a real `/embeddings` endpoint now (OpenAI-compatible, so this might be newer than what you found in your research). It's probably not free the way the chat models are — I couldn't confirm a `$0` embedding tier — but embedding calls are typically fractions of a cent regardless, so the dollar cost either way is likely negligible for one person's memory corpus. Meanwhile "local" means bundling an embedding model, which is the same category of thing (a model that needs to download) that already bit you once. Unless your connection situation's changed, I'd lean toward a small, cheap remote embedding call over reintroducing that risk to save what's probably single-digit cents a month.

**Extraction — this is the part I'd push back on hardest, and it's the same thing you already flagged yourself.** "Validated before writing" and "never stores secrets" — validated *how*, enforced *where*? If that's a prompt instruction asking the extraction model to behave, that's exactly the "I don't trust the model" problem you raised for the continuation idea, just relocated. Same fix applies: a secrets filter should be a regex/pattern check in code that runs on the output regardless of what the model intended, not a hope. That's not a nitpick — this is the layer that decides what gets permanently written to disk about you; it deserves at least as much skepticism as a code continuation did.

Second thing on extraction: running it after *every* turn means every single chat message now makes an OpenRouter call it didn't make before. Worth being precise about that, because we just found two messages ago that `chat` mode — your actual daily-use path — never touches OpenRouter at all right now; only the unreachable `orchestrate` handler does. This design would make OpenRouter a dependency of the main path for the first time, against a free tier that's rate-limited to begin with. Not a dealbreaker, just something to size — maybe extraction runs every N turns, or only on turns above some length, rather than unconditionally on all of them.

**Schema — good, one soft spot.** `entities` is doing real work in the retrieval formula (20% of the score) but isn't specified anywhere in what you sent — how do they get extracted, how do they get matched at query time? That's worth nailing down before the scoring math means anything.

**Retrieval weights (55/20/15/10)** — reasonable starting point, but be honest with yourself that these are probably borrowed from systems tuned for very different scale. Mem0/Zep are built for many users and many agents at once — that's closer to what Mira needs than what Vanta needs. For one person's memory growing over months, it's worth asking how much of this sophistication is actually earned by Vanta's real size, versus inherited because it's what the big players do. Not saying strip it down — just don't treat 55/20/15/10 as validated; expect to retune once there's real data instead of building it in as a constant.
